MLOps with DCM on Snowflake

A template for running ML workloads on Snowflake entirely as code — declared in Git, planned before applying, and promoted from DEV to PROD through CI.

Overview

The template wires together three declarative tools so that every Snowflake object an ML workload needs — features, compute jobs, schedules, model promotion — is defined in files, reviewed in pull requests, and deployed identically to each environment:

DCM projectDatabase Change Management. Declares the pipeline's code bundles and task graph; snow dcm plan diffs, snow dcm deploy converges.
Declarative Feature StoreEntities, sources and feature views as YAML; snow feature plan / apply with the same plan-then-apply model.
GitHub Actions + OIDCPRs plan DEV; merges deploy and run DEV, then promote to PROD. No stored credentials.

The ML code itself (an XGBoost regressor on synthetic transaction data) is intentionally simple. It exists to exercise the pattern: a feature step, a feature store refresh, a training step that logs to the Model Registry, and a deployment step with a quality gate. Replace any of them with your own logic without changing how things are deployed.

Design principles

  • Everything declarative, everything planned. Both the feature store and the DCM project have a read-only plan step. CI runs plans on every PR; nothing is applied without a plan having been produced.
  • One definition, many environments. The same files deploy to DEV and PROD; differences live only in manifest targets and templating.
  • Environments are isolated, compute is shared. Each environment has its own database, deployer role and service identity. The warehouse and compute pool are shared to keep a single-account setup cheap.
  • CI never writes source data. Raw data belongs to ingestion. CI deploys definitions and runs the pipeline over whatever data the environment has.
  • Promotion is gated. PROD only deploys after DEV deployed and ran end-to-end successfully. Inside each run, a model version only becomes the default if it passes the quality gate.

Identity: OIDC workload identity federation

GitHub mints a short-lived OIDC token for each job; snowflakedb/snowflake-actions@v3 passes it to the Snowflake CLI. Snowflake maps the token's issuer + subject to exactly one service user:

CREATE USER SVC_MLOPS_GH_DEV TYPE = SERVICE DEFAULT_ROLE = MLOPS_DEV_DEPLOYER;
ALTER USER SVC_MLOPS_GH_DEV SET WORKLOAD_IDENTITY = (
  TYPE = OIDC
  ISSUER = 'https://token.actions.githubusercontent.com'
  SUBJECT = 'repo:<owner>@<owner_id>/<repo>@<repo_id>:environment:dev');
  • The subject includes the GitHub environment, so only jobs declared with environment: dev can act as the DEV user, and likewise for PROD. Required reviewers on the prod environment therefore gate PROD credentials, not just the job.
  • This repo uses GitHub's immutable subject format (owner and repo IDs). Get yours with gh api repos/<owner>/<repo>/actions/oidc/customization/sub.
  • An issuer + subject pair can be bound to only one user in an account.

Network

If the account has an account-level network policy, GitHub-hosted runners are blocked by default. setup_cicd.sql attaches GITHUB_ACTIONS_POLICY (managed rule SNOWFLAKE.NETWORK_SECURITY.GITHUBACTIONS_GLOBAL) to the two service users only; the account policy is unchanged.

Authorization

Each deployer role owns its environment database and every object in it, so DCM and the feature store can create, alter and drop freely there — and nowhere else. Shared grants: USAGE on COMPUTE_WH, USAGE, MONITOR on MLOPS_COMPUTE_POOL, and EXECUTE TASK on the account. Both roles roll up to SYSADMIN.

DCM projects

Everything deployed to an environment comes from two declarative projects under resources/. Both use a manifest.yml with DEV / PROD targets and templating, both follow plan → apply, and both are deployed together, in order, by scripts/deploy_env.sh.

ProjectFolderToolOwnsLands in
Feature Store projectresources/feature_store/snow feature plan / applyWhat the features are: entity, batch source, feature view<ENV>_MLOPS_DB.FEATURE_STORE
ML Pipeline projectresources/pipeline/snow dcm plan / deployHow they're computed and used: code bundles, task graph, schedule<ENV>_MLOPS_DB.MODELS
Only the ML Pipeline project is a DCM project object (MLOPS_PIPELINE). The Feature Store project uses the Feature Store's own declarative workflow, but is versioned, planned and promoted the same way, and always in the same run.

Deploy order: bootstrap → Feature Store project → ML Pipeline project. The pipeline's tasks refresh and read the feature view, so it must exist first. At runtime the projects connect like this:

FEATURE_ENGINEERING   ─writes→      MODELS.MLOPS_PIPELINE_FEATURES       (batch source)
FEATURE_STORE_REFRESH ─refreshes→   FEATURE_STORE.MLOPS_PIPELINE_FV$V1   (dynamic table)
MODEL_TRAINING / MODEL_DEPLOYMENT ─generate_training_set(spine, [FV])→ features + label

Feature Store project

resources/feature_store/ is a declarative feature store project, deployed with snow feature plan and snow feature apply.

manifest_version: 1
type: feature_store
targets:
  DEV:  { database: DEV_MLOPS_DB, schema: FEATURE_STORE, role: MLOPS_DEV_DEPLOYER,  templating_config: DEV }
  PROD: { database: PRD_MLOPS_DB, schema: FEATURE_STORE, role: MLOPS_PROD_DEPLOYER, templating_config: PROD }
templating:
  defaults: { source_database: DEV_MLOPS_DB, source_schema: MODELS, warehouse: COMPUTE_WH }
FileKindPurpose
entities/MLOPS_TRANSACTION.yamlEntityJoin key TRANSACTION_ID — the grain at which features are unique.
datasources/MLOPS_PIPELINE_FEATURES_SRC.yamlBatchSourceA query over MODELS.MLOPS_PIPELINE_FEATURES (written by the feature-engineering task) projecting key, timestamp and feature columns.
feature_views/MLOPS_PIPELINE_FV.yamlBatchFeatureViewOffline view V1 materialized as a dynamic table; timestamp_col: TRANSACTION_DATE enables point-in-time joins.

How the pipeline consumes it

fs = FeatureStore(session, database=DB, name="FEATURE_STORE", ...)
fv = fs.get_feature_view("MLOPS_PIPELINE_FV", "V1")
df = fs.generate_training_set(
    spine_df=spine,                      # TRANSACTION_ID, TRANSACTION_DATE, label
    features=[fv],
    spine_timestamp_col="TRANSACTION_DATE",
    spine_label_cols=["UNITS_SOLD"])

The label comes from the spine (raw data), never from the feature view. The feature view's version is a templating variable (fv_version) in the DCM manifest, so training can be repointed at V2 by changing one value.

ML Pipeline project

resources/pipeline/ is the DCM project (manifest v2, object <ENV>_MLOPS_DB.MODELS.MLOPS_PIPELINE). Its definitions are written in Pipeline Builder YAML and declare the code bundles, the task graph and its schedule.

manifest_version: 2
type: DCM_PROJECT
default_target: DEV
targets:
  DEV:  { project_name: DEV_MLOPS_DB.MODELS.MLOPS_PIPELINE, project_owner: MLOPS_DEV_DEPLOYER,  templating_config: DEV }
  PROD: { project_name: PRD_MLOPS_DB.MODELS.MLOPS_PIPELINE, project_owner: MLOPS_PROD_DEPLOYER, templating_config: PROD }
templating:
  defaults:
    database: DEV_MLOPS_DB
    schema: MODELS
    warehouse: COMPUTE_WH
    compute_pool: MLOPS_COMPUTE_POOL
    cron_schedule: "0 6 * * 1 America/New_York"
    model_version: latest
    fs_schema: FEATURE_STORE
    fv_name: MLOPS_PIPELINE_FV
    fv_version: V1
  configurations:
    PROD: { database: PRD_MLOPS_DB, cron_schedule: "0 4 * * 1 America/New_York" }
assets:
  feature_engineering_bundle: { path: 'code_bundles/feature_engineering/**/*' }
  model_training_bundle:      { path: 'code_bundles/model_training/**/*' }
  model_deployment_bundle:    { path: 'code_bundles/model_deployment/**/*' }

Code bundles

Each code_bundles/<step>/ directory holds a Python entrypoint plus code_bundle.yml. Bundles use type: ml (pre-built ML runtime) and compute_type: compute_pool, so each step runs as an ML Job on MLOPS_COMPUTE_POOL.

Passing configuration into Python

Templating values flow to the scripts as environment variables declared on each task:

manifest.yml templating  →  pipeline.yml env_vars  →  os.environ in the bundle
  database                    DCM_DATABASE
  schema                      DCM_SCHEMA
  fs_schema / fv_name / fv_version → FS_SCHEMA / FV_NAME / FV_VERSION
  model_version               MODEL_VERSION   ("latest" or a pinned version)

No database names are hard-coded in Python, so the same bundles run in every environment.

Quality gate and model versioning

  • Training registers a timestamped version (PIPELINE_YYYYMMDD_HHMM) with MAE/RMSE/R² metrics.
  • Deployment evaluates the chosen version on the holdout split (same spine, same split seed as training). If RMSE exceeds the threshold it raises, the task fails, and the previous default stays live.
  • model_version = latest auto-selects the newest version; set it to a specific version name (e.g. --variable model_version=PIPELINE_20261102_1807) to pin what PROD promotes.

Deployment lifecycle

scripts/deploy_env.sh <DEV|PROD> <plan|deploy> is the single entrypoint used by CI and locally. It copies resources/ to a scratch directory, fills the manifests' <YOUR_ORG>-<YOUR_ACCOUNT> placeholder from SNOWFLAKE_ACCOUNT, and then:

#Stepplandeploy
1snow connection test✓✓
2bootstrap_env.sql — DCM project object, results stage, deploy log, feature source table (all IF NOT EXISTS)✓
3snow feature init in a scratch copy — ensures the feature store schema/metadata exist✓
4snow feature plan✓✓
5snow feature apply (never --destructive)✓
6snow dcm plan✓✓
7snow dcm deploy --alias gh-<run_id>-<sha>✓

Ordering matters: the feature view must exist before the DCM tasks that refresh and read it run, and the feature source table must exist before the feature view (whose batch source queries it) is applied — hence bootstrap → feature store → DCM.

snow feature init also exports deployed objects into sources/. Running it in a scratch copy keeps those exports from mixing with the authored definitions.

Connections

  • CI: temporary connection (-x) from SNOWFLAKE_* environment variables populated by the OIDC action.
  • Local: set SNOWFLAKE_CONNECTION=<name> to reuse a named connection and its cached login, and SNOWFLAKE_ROLE to act as a deployer role.
SNOWFLAKE_CONNECTION=my_conn SNOWFLAKE_ROLE=MLOPS_DEV_DEPLOYER \
SNOWFLAKE_ACCOUNT=MYORG-MYACCOUNT scripts/deploy_env.sh DEV plan

snow feature requires snowflake-ml-python[feature_store] in the same interpreter as the CLI: uv tool install snowflake-cli --with "snowflake-ml-python[feature_store]".

CI/CD with GitHub Actions

The PR plan (ci.yml) also authenticates as the DEV service user, but is read-only. Shared compute (COMPUTE_WH, MLOPS_COMPUTE_POOL) is omitted for clarity.

Reusable job essentials

permissions: { id-token: write, contents: read }
jobs:
  snowflake:
    environment: ${{ inputs.environment }}          # selects the OIDC subject → service user
    concurrency: { group: snowflake-${{ inputs.environment }}, cancel-in-progress: false }
    env:
      SNOWFLAKE_ACCOUNT: ${{ vars.SNOWFLAKE_ACCOUNT }}
      SNOWFLAKE_ROLE: ${{ inputs.target == 'PROD' && 'MLOPS_PROD_DEPLOYER' || 'MLOPS_DEV_DEPLOYER' }}
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv tool install --python 3.12 snowflake-cli --with "snowflake-ml-python[feature_store]"
      - uses: snowflakedb/snowflake-actions@v3
        with: { use-oidc: true, oidc-audience: snowflakecomputing.com }
      - run: bash scripts/deploy_env.sh "${{ inputs.target }}" "${{ inputs.mode }}"
  • Only one variable: SNOWFLAKE_ACCOUNT (repo variable, not a secret).
  • Concurrency per environment prevents two deploys from racing on the same DCM project lock.
  • Manual PROD approval: add required reviewers to the prod GitHub environment; the PROD job (and its credentials) then waits for sign-off.

Suggested Git flow

  1. Branch, change definitions or code bundles.
  2. Open a PR — review the feature store and DCM plans in the ci run.
  3. Merge — DEV deploys and runs; on success PROD deploys and runs.
  4. Every DCM deploy is recorded with an alias (snow dcm list-deployments); every model version is in the Model Registry; every change is a commit.

Operations

Run the pipeline once

scripts/run_pipeline.sh <DEV|PROD> enables the graph (SYSTEM$TASK_DEPENDENTS_ENABLE), runs EXECUTE TASK on the root, polls TASK_HISTORY until the finalizer completes, fails on any failed task, checks that a DEPLOYED row was logged, and re-suspends the root on exit.

Because the script re-suspends the root, the weekly cron only fires where you deliberately leave it resumed: ALTER TASK <DB>.MODELS.MLOPS_PIPELINE_ROOT RESUME.

Monitor

-- task runs
SELECT NAME, STATE, ERROR_MESSAGE, SCHEDULED_TIME, COMPLETED_TIME
FROM TABLE(DEV_MLOPS_DB.INFORMATION_SCHEMA.TASK_HISTORY(
  SCHEDULED_TIME_RANGE_START => DATEADD('hour', -24, CURRENT_TIMESTAMP())))
WHERE NAME LIKE 'MLOPS%' ORDER BY SCHEDULED_TIME DESC;

-- promotions
SELECT * FROM DEV_MLOPS_DB.MODELS.MLOPS_PIPELINE_DEPLOY_LOG ORDER BY DEPLOYED_AT DESC;

-- feature view refreshes
SELECT * FROM TABLE(DEV_MLOPS_DB.INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(
  NAME => 'DEV_MLOPS_DB.FEATURE_STORE.MLOPS_PIPELINE_FV$V1'));

Roll back

  • Definitions: revert the commit and merge; the deploy workflow converges both environments to the reverted state.
  • Model: set the default version back — ALTER MODEL …MLOPS_PIPELINE_MODEL SET DEFAULT_VERSION = '<version>' — or pin model_version.

Tear down an environment

snow dcm purge  <DB>.MODELS.MLOPS_PIPELINE --target <T> --force   # drops managed objects
snow dcm drop   <DB>.MODELS.MLOPS_PIPELINE                       # drops project metadata
snow feature plan --delete … then apply --destructive              # removes feature store objects
Purge is irreversible and drops data in managed objects. snow dcm drop alone leaves the managed objects behind.

Adapting the template

GoalChange
Use your own dataLand it in <ENV>_MLOPS_DB.RAW via your ingestion; update the feature-engineering bundle and the spine in the training/deployment bundles.
Change featuresEdit the feature-engineering bundle and the batch source query. For a breaking change, add MLOPS_PIPELINE_FV version: V2, deploy, then bump fv_version in the DCM manifest.
Change the modelEdit code_bundles/model_training/; keep logging to the registry with metrics.
Change promotion rulesEdit the quality gate in code_bundles/model_deployment/.
Add a pipeline stepAdd a resource: code_bundle + resource: task to pipeline.yml, an asset in the manifest, and wire predecessors.
Add an environment (e.g. STAGE)New target + templating config in both manifests, a database/role/user in setup_cicd.sql, a GitHub environment, and a job in deploy.yml.
Use your own repoUpdate the two OIDC SUBJECT values in setup_cicd.sql and set the SNOWFLAKE_ACCOUNT variable.

Troubleshooting

SymptomCause / fix
snow feature missing or failing to importsnowflake-ml-python[feature_store] isn't in the CLI's interpreter. Install them together (uv tool install snowflake-cli --with …); Python 3.12 is a safe version.
Account mismatch: manifest target … specifies '<YOUR_ORG>-<YOUR_ACCOUNT>'Run through deploy_env.sh (fills the placeholder) or set account_identifier to the canonical ORG-ACCOUNT form.
Schema … is not initialized as a feature storeRun snow feature init --target <T> once (deploy mode does this automatically).
Feature view exposes the label or string columnsA table-backed BatchSource's columns: doesn't project. Use an explicit query listing only key, timestamp and features.
Plan always shows UPDATE_SOURCEBatchSource description isn't persisted; remove it.
… already exists, but current role has no privileges on it (DCM plan)An object is owned by another role. Code bundles are NOTEBOOK PROJECT objects: GRANT OWNERSHIP ON ALL NOTEBOOK PROJECTS IN SCHEMA ….
OIDC Authenticator for Issuer … and Subject … already existsAnother user holds that subject. ALTER USER <old> UNSET WORKLOAD_IDENTITY first.
Runner can't connect (network policy)Attach GITHUB_ACTIONS_POLICY (managed rule GITHUBACTIONS_GLOBAL) to the service users.
invalid type [TIMESTAMP_TZ] for parameter 'SCHEDULED_TIME_RANGE_START'TASK_HISTORY expects TIMESTAMP_LTZ.
DCM deploy hangs / “currently being executed by another process”A previous deploy still holds the project lock. Find the running EXECUTE DCM PROJECT query and cancel it; workflow concurrency groups prevent this in CI.
